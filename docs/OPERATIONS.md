# Обслуговування, обмеження та приватність

## Черги й статус

```bash
bash scripts/bot.sh metrics
bash scripts/bot.sh inspect-outbox
```

Метрики містять розміри черг, кількість помилок/невизначених доставок та використання Groq за 24 години. `System.Diagnostics.Metrics` публікує лічильники виконання й помилок. Логи AI містять тривалість, технічний номер задачі, модель і кількість токенів. Вміст діалогів, нотаток, зізнань, джерел, ключі й повні HTTP URL/тіла в логи не записуються. EF SQL-логи та стандартне логування HttpClient вимкнені, оскільки Telegram включає токен у URL.

`inspect-outbox` показує тільки технічні метадані максимум 100 задач. Порядок визначається ID. Доставлені частини мають `TelegramMessageId` і не надсилаються повторно.

## Невизначена доставка зізнання

При timeout/обриві з’єднання після sendMessage або рестарті в момент відправлення частина отримує `delivery_unknown`. Бот не повторює її автоматично. Інші частини цього подання чекають перевірки. Власник:

1. Зупиняє Run, щоб не було паралельного воркера.
2. Запускає `inspect-outbox` і знаходить ID частини та номер операції.
3. Перевіряє повідомлення в службовому каналі.
4. Якщо частина вже є в каналі, позначає її доставленою з фактичним message ID. У посиланні на повідомлення це останнє число.

```bash
bash scripts/bot.sh mark-delivered 123 --message-id 456
```

Якщо після перевірки власник вирішує надіслати частину повторно:

```bash
bash scripts/bot.sh retry-delivery 123 --accept-duplicate-risk
```

Повтор невизначеної доставки може створити дубль — Telegram sendMessage не має універсального ключа ідемпотентності. Для відомої відмови зі статусом `failed` прапорець не потрібний:

```bash
bash scripts/bot.sh retry-delivery 123
```

Після цього знову натисни Run. Бот відправить тільки недоставлені частини та оновить результат подання. Користувач також може повторити відому невдалу доставку кнопкою в розділі зізнань. Команди не редагують і не видаляють повідомлення каналу.

Для невизначеної доставки звичайної відповіді/меню автоматичного повтору теж немає; наступні частини цієї операції скасовуються. Користувач може повторно відкрити меню чи написати запит. Це обережна поведінка за неможливості встановити факт доставки.

## Telegram ID і старий webhook

Зупини бота перед операторськими перевірками.

```bash
bash scripts/bot.sh channel-id
```

Ця команда перемикає тимчасове читання на `channel_post` і показує лише ID каналів з доступних оновлень. Якщо список порожній, вручну напиши нове тестове повідомлення у свій службовий канал і повтори команду. Бот має бути адміністратором каналу. Команда не друкує текст повідомлень та не відправляє повідомлень від твого імені. Звичайний Run повертає отримання `message` та `callback_query`.

Якщо тестовий токен раніше використовував webhook, видали саме цей webhook без очищення черги updates:

```bash
bash scripts/bot.sh delete-webhook
```

Тільки після цього запусти Run. Не виконуй дію для токена іншого робочого бота.

## Налаштування ресурсів

Початкові значення, не обіцянка квот сервісів:

| Налаштування | Значення |
|---|---|
| AI паралельність | 2 |
| HTTP timeout Groq | 45 с |
| Бюджет одного AI-виклику з очікуванням квоти | 100 с |
| Максимальне очікування задачі в черзі | 300 с |
| Невиконані AI-задачі одного користувача | 20; наступний текст зберігається як невідповіданий |
| Inbox | до 10 000 очікуваних оновлень; за переповнення offset не просувається |
| Telegram | до 20 повідомлень/с глобально, пауза 1,1 с для чату, 3,1 с для каналу |
| Нотатка/зізнання | без ліміту 1000 символів; аварійна межа — 4096 окремих частин чернетки |
| Вихідний текст | до 4000 UTF-16 одиниць, для тіла частини зізнання 3800 |
| Історія настрою | 5 записів на сторінці, 7 календарних днів у періоді |
| Довідкові фрагменти | до 3, до 1200 приблизних токенів |
| Groq | 25 RPM, 8000 TPM, 900 RPD, 190000 TPD; звірити в кабінеті |

Межа 4096 частин чернетки потрібна для аварійного захисту пам’яті сервера; це приблизно до 16 млн символів, якщо кожна частина наближається до ліміту Telegram. Коли межу досягнуто, нова частина відхиляється з явним поясненням, уже збережений текст не обрізається. Не використовуй це як спосіб масового завантаження документів.

Оцінювання токенів локальне й приблизне: UTF-8 байти / 3 плюс службовий запас. Резервуються також вихідні токени; після відповіді використання уточнюється з `usage`. Ліміти зберігають журнал у БД, включно із підсумками, та враховують 429/Retry-After. Фактичні квоти Groq мають пріоритет. Перевірка 1000 користувачів із fake AI не означає підтримку 1000 одночасних безкоштовних Groq-чатів.

Після зміни типових лімітів або моделей перевір профілі параметрів. Нові моделі не отримують reasoning-параметри автоматично. Основна й резервна моделі задаються через Secrets; вихідні відповіді очищуються від think-блоків.

## Зберігання й очищення

| Дані | Фактична поведінка |
|---|---|
| Настрій і нотатки | До повного видалення профілю |
| Відповідана переписка | Стиснення після понад 20 реплік, щонайменше 10 останніх лишаються дослівно |
| Невідповідані репліки | Збережені до очищення пам’яті/профілю |
| Пам’ять | До очищення пам’яті/профілю, не очищується виходом із чату |
| Чернетки | До відправлення, збереження, скасування або підтвердженої втрати при /menu |
| Зізнання в локальній черзі | Текст частини стирається після підтвердженої доставки; failed/unknown зберігаються до розв’язання або видалення профілю |
| Inbox payload | Стирається після завершення/остаточної помилки; технічні update ID — 7 днів |
| Outbox звичайних повідомлень | Текст і адресат стираються після кінцевого результату; технічні рядки — 7 днів |
| Повідомлення про видалення | Тимчасова адреса доставки без профілю; очищення після відправлення або максимум через годину роботи планувальника |
| Технічний журнал Groq | 2 дні, без текстів і user ID |
| Історія occurrence нагадувань | Кінцеві записи — 30 днів |

Планове очищення працює тільки коли застосунок запущений. Повне видалення профілю одразу каскадно видаляє пов’язані таблиці та персональний Inbox. Воно не викликає Telegram deleteMessage/editMessageText. Нова команда `/start` створює новий незалежний UUID профілю; результати старого UUID не можуть його відновити.

Настрій у контексті початково вимкнений. Після вимкнення не додаються нові записи й похідні відповіді, позначені як створені з контекстом настрою. Підсумок складається тільки з завершених користувацьких реплік, без автоматично доданих записів настрою.

## Резервні копії та відновлення без повернення видаленого

Застосунок не створює власних дампів і не налаштовує автоматичні backups. Replit/Railway можуть мати свої snapshots/checkpoints; у наданому коді немає доступу для їх видалення. Фактичний строк зберігання треба взяти з налаштувань свого акаунта. Перед робочим запуском встанови обрану політику, наприклад щоденний backup зі строком 7 днів, якщо тариф це підтримує, і перевір видалення прострочених копій у панелі.

**Безпечна процедура для цієї версії:** не відновлювати старий повний персональний дамп поверх живої бази. Для відновлення після втрати БД створи чисту БД, застосуй `migrate` і повторно імпортуй книги. Користувачі почнуть заново через `/start`. Це втрачає також невидалені особисті записи, зате не повертає раніше видалені.

Якщо потрібно зберегти історію під час аварійного відновлення, до ввімкнення такого режиму потрібен окремий журнал видалень поза backup і процедура повторного застосування видалень. Ця версія не обіцяє такого вибіркового відновлення; автоматичне відновлення персональних snapshots заборонене операторською процедурою.

## Типові проблеми

Якщо після старих експериментів лишилася помилка `Couldn't find a valid ICU package`, переконайся, що `replit.nix` імпортований у корінь, і перезапусти Shell/середовище для встановлення його залежностей. Бот використовує культуру `uk-UA`, тому режим `DOTNET_SYSTEM_GLOBALIZATION_INVARIANT=1` не підходить: видали цю змінну з Secrets або встанови `0`. Не підмінюй установлення ICU вимкненням локалізації.

Короткі збої запитів до БД повторюються воркерами. При втраті окремого з’єднання, яке утримує блокування єдиного poller, застосунок штатно завершується з кодом `1`: Railway може перезапустити його, у Replit треба знову натиснути Run. Це запобігає одночасній роботі без підтвердженого блокування; під час недоступності БД бот не обіцяє приймання нових повідомлень.

| Симптом | Що перевірити |
|---|---|
| `Set ... in Secrets` | Додай названий Secret і перезапусти |
| SDK не запускається | Перезавантаж Shell для застосування `replit.nix`; перевір Linux x64/arm64 та системні ICU/OpenSSL |
| NuGet locked-mode error | Не змінюй пакети окремо від lock-файлів; для свідомого оновлення виконай звичайний restore і повтори тести |
| Readiness 503 | Доступність PostgreSQL, правильний DATABASE_URL, міграції, воркер |
| Telegram 401 | Неправильний або відкликаний токен |
| Telegram 409 / another instance | Зупини інший poller/webhook із цим токеном |
| Groq 401/403 | Ключ і права на моделі; нескінченні retry не виконуються |
| Часті черги/429 | Звір фактичні квоти Groq та зменш навантаження |
| Зізнання не надходить | ID каналу, права бота, inspect-outbox |
| Пошук не знаходить потрібне | list-books, статус джерела, наявність текстового шару, search-books; лексичний пошук не розуміє всі перефразування |
